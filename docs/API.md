# 安知 AnZhi — API 接口文档

> 版本：V1.0
> 基础地址：`http://127.0.0.1:8000`
> 数据格式：`application/json`
> 交互式文档：启动后端后访问 `/docs`（Swagger UI）
> 依据：PROJECT_SPEC.md 第三十二、三十四、三十六、三十八 ~ 四十二节

---

## 1. 通用约定

### 1.1 响应格式

**成功：** 直接返回业务数据（HTTP 200 / 201）

**失败：** 统一错误结构

```json
{
  "detail": "错误说明"
}
```

### 1.2 状态码

| 状态码 | 含义 |
|:--:|---|
| 200 | 成功 |
| 201 | 创建成功 |
| 400 | 请求参数错误 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 422 | 参数校验失败（FastAPI 自动） |
| 500 | 服务器内部错误 |
| 503 | 上游 AI 服务不可用 |

### 1.3 分页参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 页码，≥1 |
| `page_size` | int | 20 | 每页条数，1~100 |

分页响应：

```json
{
  "total": 128,
  "page": 1,
  "page_size": 20,
  "items": []
}
```

### 1.4 客户端接入

Flutter 端通过 `lib/services/api_client.dart` 统一发起请求，**页面不直接调用 HTTP**。

| 运行环境 | 后端地址 |
|---|---|
| Android 模拟器 | `http://10.0.2.2:8000`（默认值，模拟器映射到宿主机） |
| 真机（同一局域网） | 电脑局域网 IP，用 `--dart-define=ANZHI_API_BASE_URL=http://192.168.1.5:8000` 指定 |
| Windows / macOS 桌面 | `http://127.0.0.1:8000` |

客户端约定：

- 普通接口超时 10 秒（`ApiConfig.timeout`）；网络失败、超时、非 2xx、非 JSON
  响应**一律翻译成中文提示**，页面只处理一种异常类型
- **AI 问答超时 60 秒**（`ApiConfig.aiTimeout`）。大模型生成一段回答通常要十几秒，
  沿用 10 秒会让绝大多数正常提问被误判为超时
- 值为 `null` 或空串的查询参数会被剔除，避免后端收到 `category_id=null` 而返回 422
- 错误提示优先取后端 `errors[0].message`，其次 `detail`，最后才退化成
  「请求失败（HTTP xxx）」—— **不要展示纯状态码**，用户看不懂
- 后端只返回 `is_published = true` 的内容，客户端必须正确处理「成功但为空」
- 请求失败时展示后端给的中文说明，**绝不伪造一条 AI 回答或占位数据**

## 3. AI 问答

### `POST /api/chat`

**说明：** AI 安全问答核心接口（PROJECT_SPEC 第三十六节）

**请求体：**

```json
{
  "message": "宿舍发生火灾怎么办？",
  "category": "消防安全",
  "history": []
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `message` | string | ✅ | 用户问题，1~1000 字符 |
| `category` | string | ❌ | 指定分类，不传则自动判断 |
| `history` | array | ❌ | 多轮对话上下文 |

**响应 200：**

```json
{
  "question": "宿舍发生火灾怎么办？",
  "category": "消防安全",
  "risk_level": "high",
  "answer": "立即撤离，不要贪恋财物……",
  "steps": [
    "保持冷静，大声呼喊提醒室友",
    "用湿毛巾捂住口鼻，低姿弯腰撤离",
    "不要乘坐电梯，走安全通道",
    "到达安全区域后拨打 119"
  ],
  "sources": ["《中华人民共和国消防法》", "应急管理部消防救援局"],
  "warning": "⚠️ 生命安全优先，切勿返回火场取物。"
}
```

**字段说明：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `risk_level` | string | `low` / `medium` / `high` |
| `steps` | string[] | 可执行步骤，高风险时非空 |
| `sources` | string[] | 来源引用，V1.0 可为空，V2.0 RAG 填充 |
| `warning` | string | 安全警告，medium / high 时非空 |

**错误：**

后端把失败原因翻译成一句可以直接展示给用户的中文，客户端不需要自己判断
「是没配 Key 还是超时」。

| 状态码 | `detail` 的含义 | 客户端应如何提示 |
|:--:|---|---|
| 422 | 参数不合法（`message` 为空/全空白/超过 1000 字符） | 直接展示 `errors[0].message` |
| 502 | DeepSeek 返回了无法解析的内容 | 展示「服务暂时不可用，请稍后再试」 |
| 503 | 未配置 `DEEPSEEK_API_KEY`，或上游鉴权失败、限流 | 原样展示，提示需要联系管理员 |
| 504 | 调用 DeepSeek 超时（默认 60 秒） | 建议稍后重试 |

> **未配置 Key 时返回 503 而不是 500，是刻意的。** 这是一个「部署没配好」的状态，
> 不是程序出错，用户看到 500 只会以为 App 坏了。当前仓库没有配置 Key，
> 所以本接口现在返回的正是 503 + `AI 服务未配置，请联系管理员在后端 .env 中设置 DEEPSEEK_API_KEY`。
> **因此 V1 的 AI 问答尚未端到端跑通** —— 链路代码已完成，缺的是一把真实的 Key。

422 的响应体会带上结构化的字段错误（`errors[0].message` 可直接展示）：

```json
{
  "detail": "参数校验失败：message 问题不能为空",
  "errors": [
    { "field": "message", "message": "问题不能为空", "type": "value_error" }
  ]
}
```

**安全约束（PROJECT_SPEC 第十、十一节、AI_RULES 第十节）：**

> - 高风险问题：回答简洁，优先给出应急措施，**不做长篇科普**
> - 禁止鼓励冒险、禁止危险实验步骤、禁止娱乐化处理紧急情况
> - 信息不足时不得过度确定

**当前实现边界（不要高估）：**

链路：`用户问题 → ChatService → DeepSeek → 规范化 → SafetyGuard → 最终回答`

- ✅ 提示词里已写入上述约束，并强制模型返回结构化 JSON
- ✅ 结构性兜底：字段缺失不崩溃；风险等级无法识别时**降级为中风险而非低风险**
  （把低风险误判成中风险只是多一句警告，把高风险误判成低风险会害人）
- ✅ **`SafetyGuard` 确定性审查**（阶段 9，见下）
- ⚠️ 审查层是**规则**，不是万能的判断力。它能拦住已知的危险表述，
  拦不住它没被教过的说法。**不要宣称「AI 输出已经安全」**，
  只能说「已知的危险做法不会原样送到用户面前」。

### `SafetyGuard` 做了什么

一个不调用大模型的确定性审查层，位于模型输出与用户之间。
之所以不用第二次大模型调用：那只是把「模型可能出错」叠了两次，
而且会让「这条回答为什么被拦下」变得不可复现、不可测试。

| 能力 | 行为 |
|---|---|
| **危险操作拦截** | 命中即整条替换为兜底话术，`steps` 与 `sources` 一并清空，`risk_level` 强制为 `high` |
| **风险等级只抬不降** | 问题含「触电了」「闻到燃气味」等正在发生的危险 → 至少 `high`；含「火灾」「诈骗」等风险主题 → 至少 `medium`。**任何情况下都不降级** |
| **警告补齐** | `medium` / `high` 缺警告时补通用提示；紧急场景的警告若不含求助电话，追加提示 |
| **过度确定** | 命中「绝对安全」「万无一失」等措辞不拦截，但保证带警告并记录 |
| **不编造** | 高风险回答缺 `steps` 时**只记录不补** —— 编造一条「看起来专业」的操作建议比明说「请听从专业人员指挥」危险得多 |

**否定判定：** 提示词要求模型说明「什么不要做」，所以正确的回答里
必然包含危险短语本身（「切勿返回火场取物」里有「返回火场」）。
直接用子串匹配会把最该保留的回答全部误杀，因此危险短语先在**小句内**
做否定判定：同一个小句里出现「不要 / 切勿 / 严禁」即视为劝阻。
「不要犹豫，立即返回火场取物」仍会被拦下 —— 否定词在前一个小句，不算数。

**拦截后的响应长这样：**

```json
{
  "risk_level": "high",
  "answer": "这条回答包含可能造成伤害的做法，已被安全审查拦下，不能作为处置依据。请立即拨打 119（火警）/ 120（急救）/ 110（报警），并听从专业人员指挥。",
  "steps": [],
  "sources": [],
  "warning": "以上内容仅供参考。若情况紧急或已有人受伤，请立即拨打 119（火警）/ 120（急救）/ 110（报警），并听从专业人员指挥。"
}
```

> 返回 **200** 而不是错误码：这不是请求失败，而是一条已被处理过的回答。
> 客户端不需要为「被拦下」写额外分支 —— 它拿到的仍然是一条
> `risk_level: high` 且带警告的正常回答。

### `GET /api/knowledge/{id}`

**说明：** 知识详情

> **本接口保持只读，没有任何副作用** —— 既不累加浏览量，也不写浏览历史。
> 这两件事都挂在下方 `POST /api/knowledge/{id}/view` 上：
> 带副作用的 `GET` 会被浏览器预取、爬虫、客户端自动重试各算一次，
> 统计出来的数字没有意义，历史记录也会凭空多出一堆用户没看过的条目。

**响应 200：**

```json
{
  "id": 1,
  "title": "宿舍消防安全",
  "category_id": 1,
  "category_name": "消防安全",
  "summary": "宿舍常见火灾隐患与预防措施",
  "content": "……正文……",
  "risk_level": "medium",
  "image_url": null,
  "source": "应急管理部",
  "author": "安知编辑部",
  "view_count": 42,
  "is_favorited": false,
  "created_at": "2026-09-30T10:00:00"
}
```

**`is_favorited` 是按人算的：** 它表示「**你**收藏过这条没有」，
而不是「有没有人收藏过」。匿名访问时恒为 `false` ——
没有身份就无从判断，这个 `false` 的实际含义是「不知道你是谁」，
客户端**不能**据此认定「未收藏」。详情页要用它点亮收藏按钮，
就必须带着 token 发这个请求。

**错误：** `404` —— 知识不存在或未发布

---

### `POST /api/knowledge/{id}/view`

**说明：** 记录一次浏览，`view_count` 加一；**带登录身份时同时记一条浏览历史**

**鉴权：** **可选。** 带有效 token 时按该用户记录历史；不带 token 也照样
返回 `200` 并正常计数，**不会**返回 `401`。

**请求体：** 无（空对象 `{}` 即可）

**响应 200：**

```json
{ "view_count": 43 }
```

**错误：** `404` —— 知识不存在或未发布

**为什么历史写在这里，而不是详情接口或单独一个接口：**

- 详情 `GET` 必须保持无副作用（理由见下），写历史不能挂在它上面。
- 单独开一个 `POST /api/history` 让客户端在打开详情时多调一次，
  等于同一次浏览发两个请求，而且客户端重试会重复记。
  挂在本接口上，详情页本来就要调它来计数，顺带就完成了。
- 放在计数**之后**：走到那里说明可见性已经确认过，
  不必再查一次「这条能不能看」。

> 未登录时不记历史的理由，见第 6 节末尾。

**为什么不做成 `GET` 详情接口的副作用：**

- `GET` 应当是幂等、可缓存的。带副作用的 `GET` 会被浏览器预取、
  爬虫、客户端的自动重试各加一次，统计出来的数字没有意义。
- 计数失败**不应该**让一次正常的阅读变成错误页。客户端的
  `KnowledgeApi.recordView()` 因此刻意吞掉异常并返回 `null` ——
  浏览量是锦上添花的数据，正文能读到才是正事。

**并发：** 服务端用 SQL 层的 `view_count = view_count + 1` 而不是
「读出来 +1 再写回」。后者在两个请求同时到达时会丢更新。

## 5. 收藏

> **本节三个接口都要求登录**（见第 11 节）。未带有效 token 一律返回
> `401` 与 `{"detail": "请先登录"}`，且所有查询都以当前用户的 `id` 为条件 ——
> 收藏是「谁的数据」问题，绕开身份没有意义。

### `POST /api/favorites`

**请求体：**

```json
{ "knowledge_id": 1 }
```

**响应 201**（这次新建了记录）：

```json
{ "id": 1, "knowledge_id": 1, "created_at": "2026-09-30T10:00:00" }
```

**响应 200**（这条**已经**在收藏里，返回的是那条已有记录）：

```json
{ "id": 1, "knowledge_id": 1, "created_at": "2026-09-30T10:00:00" }
```

> **重复收藏是幂等的，二选一里选了「幂等」而不是「报 400」。**
> 收藏按钮是个开关，用户要的是「这条在我的收藏里」这个**状态**，
> 不是「插入了一行」。为了这个状态再让他处理一次报错，是把实现细节
> 泄露成了用户体验问题。
>
> `201` 与 `200` 的区别如实反映了「这次到底有没有新建」——
> 既保持了幂等，又没有把两种结果混为一谈。

**错误：** `404` —— 知识不存在或未发布

> 未发布的内容在接口层一律视为不存在（`404` 而非 `403`），
> 与 `GET /api/knowledge/{id}` 的措辞完全一致，
> 否则这个接口就成了探测「有哪些未发布内容」的工具。

### `DELETE /api/favorites/{knowledge_id}`

**响应 204：** 无内容

> **永远返回 `204`，取消一条没收藏过的也算成功。**
> 理由同上：用户要的是「这条不在我的收藏里」，而这个状态已经成立了。
> 对不存在的记录返回 `404` 只会让客户端的开关逻辑多一个无意义的错误分支。

### `GET /api/favorites`

**说明：** 我的收藏列表（PROJECT_SPEC 第三十九节），按收藏时间倒序

**查询参数：** `page` / `page_size`（同第 1.3 节，`page_size` 上限 100）

**响应 200：**

```json
{
  "total": 2,
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "id": 7,
      "knowledge_id": 1,
      "created_at": "2026-09-30T10:00:00",
      "knowledge": {
        "id": 1,
        "title": "宿舍消防安全",
        "category_id": 1,
        "category_name": "消防安全",
        "summary": "宿舍常见火灾隐患与预防措施",
        "risk_level": "medium",
        "image_url": null,
        "created_at": "2026-09-30T09:00:00"
      }
    }
  ]
}
```

> **每项内嵌一个 `knowledge`**（结构与 `GET /api/knowledge` 的列表项相同，
> 同样不含正文）。收藏列表要显示标题和分类，内嵌之后一次请求就够了；
> 只返回 `knowledge_id` 会让客户端为了渲染一页 20 条再发 20 次详情请求。

> **已下架（未发布）的知识不会出现在列表里，也不计入 `total`。**
> 收藏记录本身还在数据库里 —— 内容重新发布后它会自然回到列表中。

## 6. 历史记录

> **本节三个接口都要求登录**（见第 11 节）。未带有效 token 一律返回
> `401` 与 `{"detail": "请先登录"}`，且所有查询都以当前用户的 `id` 为条件 ——
> 看过什么、什么时候看的，都是隐私，绕开身份没有意义。
>
> **但写入历史的接口不在这里。** 记录一次浏览挂在
> `POST /api/knowledge/{id}/view` 上（第 4 节），它用的是**可选鉴权**：
> 未登录照样计数、返回 `200`，只是不记历史。详见下方说明。

### `GET /api/history`

**说明：** 我的浏览历史列表（PROJECT_SPEC 第四十节），按 `viewed_at` 倒序，
同一时间按 `id` 倒序兜底

**查询参数：** `page` / `page_size`（同第 1.3 节，`page_size` 上限 100）

**响应 200：**

```json
{
  "total": 2,
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "id": 12,
      "knowledge_id": 1,
      "viewed_at": "2026-09-30T10:00:00.123456",
      "knowledge": {
        "id": 1,
        "title": "宿舍消防安全",
        "category_id": 1,
        "category_name": "消防安全",
        "summary": "宿舍常见火灾隐患与预防措施",
        "risk_level": "medium",
        "image_url": null,
        "created_at": "2026-09-30T09:00:00"
      }
    }
  ]
}
```

> **每项内嵌一个 `knowledge`**，结构与 `GET /api/favorites` 完全一致
> （即 `GET /api/knowledge` 的列表项，不含正文）。理由也相同：
> 历史列表要显示标题和分类，内嵌之后一次请求就够了。

> **已下架（未发布）的知识不会出现在列表里，也不计入 `total`。**
> 与收藏一样，历史记录本身还在数据库里 —— 内容重新发布后会自然回来。

> **`viewed_at` 是不带时区的 UTC。** 后端统一用 `datetime.utcnow()`，
> pydantic 序列化出来就是上面这种 `2026-09-30T10:00:00.123456`，
> 结尾**没有 `Z`**。客户端必须按 UTC 解释再转本地时间：
> Dart 的 `DateTime.parse` 遇到不带时区的字符串会当成本地时间，
> UTC+8 的机器上「刚刚看过」会显示成「8 小时前」——
> 这个错误不会抛异常，只会让数字悄悄不对。客户端统一走
> `lib/core/relative_time.dart` 的 `parseServerTime()` 处理。

### `DELETE /api/history/{knowledge_id}`

**响应 204：** 无内容

> **永远返回 `204`，删除一条本来就没有的也算成功**（幂等）。
> 用户要的是「这条不在我的历史里」，而这个状态已经成立了。

### `DELETE /api/history`

**说明：** 清空我的全部历史

**响应 204：** 无内容

> 清空**只清当前用户自己的**记录，别人的不受影响。
> 这是本模块唯一不可撤销的操作，客户端的「清空浏览历史」按钮
> 因此必须弹确认框再执行。

### 历史是怎么被写进去的

写入不在本节，而在 `POST /api/knowledge/{id}/view`：

- **同一条知识反复看只留一行**，再次浏览是把 `viewed_at` 更新为当前时间，
  而不是插入新记录 —— 否则反复打开同一篇会堆成一长串，
  「最近看过」也就失去意义了。
- **并发下不会冒成 `500`。** 两个请求同时判定「还没有记录」而各自插入时，
  唯一约束会触发 `IntegrityError`；服务层捕获后回滚并改为更新那一条。
  一次正常的浏览不该因为抢跑而变成错误页。
- **未登录浏览不记历史**，但计数照常。这是刻意的：匿名用户的浏览没有
  归属，记在任何人头上都是错的；而浏览量是内容质量的数据，与身份无关。

| `POST` | `/api/posts` | 发布帖子 | 阶段 12d |

### `GET /api/posts`

**鉴权：** 不需要。社区内容公开，未登录也能读。

**查询参数：** 分页参数见 1.3，另有两个筛选：

| 参数 | 类型 | 说明 |
|---|---|---|
| `category_id` | int | 只看某个分类的帖子 |
| `keyword` | string | 在标题与正文里搜 |

两个筛选都在**服务端**执行，不是取回整页再本地过滤 —— 否则「第 1 页
20 条」里筛出来的条数会和 `total` 对不上。

**响应：**

```json
{
  "total": 27,
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "id": 1,
      "title": "宿舍用电的几点提醒",
      "summary": "不要在一个插排上同时接大功率电器。电线过热是宿舍火灾最常见的原因……",
      "category_id": 2,
      "category_name": "用电安全",
      "author": { "id": 3, "name": "小艾" },
      "like_count": 3,
      "comment_count": 1,
      "created_at": "2026-09-30T10:00:00.123456"
    }
  ]
}
```

**列表项没有 `content`。** `summary` 由正文截断而来（去换行、超长加省略号），
不是独立存储的字段 —— 数据库里只有 `content`。列表页拿到的文字够显示两三行，
要读全文得请求详情接口。

**`author` 只有 `name`，没有 `username`。** 用户名是登录凭据的一半，
公开它等于把每个发帖人的登录名挂在网上，配合撞库尝试很不划算。
`name` 取昵称，没设昵称时退回用户名。

**`category_id` / `category_name` 可以是 `null`。** 帖子允许不属于任何分类，
这是数据库层面就允许的情况，不是脏数据。前端此时不画分类标签。

**排序：** `created_at` 倒序，同一时刻的按 `id` 倒序兜底。

### `GET /api/posts/{id}`

**鉴权：** 不需要。

**响应：** 与列表项同构，但用 `content`（全文）替换 `summary`：

```json
{
  "id": 1,
  "title": "宿舍用电的几点提醒",
  "content": "不要在一个插排上同时接大功率电器。……",
  "category_id": 2,
  "category_name": "用电安全",
  "author": { "id": 3, "name": "小艾" },
  "like_count": 3,
  "comment_count": 1,
  "created_at": "2026-09-30T10:00:00.123456"
}
```

**已隐藏的帖子返回 `404` 而不是 `403`：** 未发布的帖子对普通用户等同于不存在，
返回 `403` 反而等于确认了「这个 id 上有东西」。

**响应示例：**

```json
{ "detail": "帖子不存在或已删除" }
```

**`created_at` 是 naive UTC。** 全项目统一（见 `backend/app/database/base.py`
的 `utcnow`），序列化出来**不带 `Z`**。客户端必须显式按 UTC 解释，
否则 UTC+8 下会整体偏 8 小时 —— 这个坑不会报错，只会让「刚刚」变成「8 小时前」。
前端统一走 `lib/core/relative_time.dart` 的 `parseServerTime`。

### `GET /api/posts/{id}/comments`

**鉴权：** 不需要。

**查询参数：** 分页参数见 1.3。

**响应：**

```json
{
  "total": 2,
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "id": 1,
      "content": "补充一点：充电器长期插着也会发热。",
      "author": { "id": 3, "name": "小周" },
      "created_at": "2026-09-30T11:00:00.123456"
    }
  ]
}
```

**排序是时间正序，与帖子列表相反。** 帖子是「最新发生了什么」，
评论是「这场对话怎么走到这里的」—— 倒着读接不上。
同一时刻的按 `id` 正序兜底。

作者同样只有 `name`，没有 `username`。

帖子不存在或已隐藏时返回 `404`（detail 与详情接口相同）。

### `POST /api/posts/{id}/comments`

**鉴权：需要。** 未登录返回 `401`「请先登录」。

**请求体：**

```json
{ "content": "补充一点：充电器长期插着也会发热。" }
```

**响应 `201`：** 与列表项同构的单条评论（`id` / `content` / `author` / `created_at`）。

**校验：**

| 情况 | 结果 |
|---|---|
| 内容为空或只有空白 | `422`（`content` 先 `strip()` 再判空） |
| 去空白后超过 500 字 | `422` |
| 帖子不存在或已隐藏 | `404`，且**不会**留下任何记录 |

长度限制按 `strip()` **之后**的文本算 —— 前后多打了两个空格不该被拒。
入库的也是去空白之后的文本。

**发表成功会同步 `posts.comment_count`。** 这个字段是列表上显示给用户的
数字，由业务层维护。实现上不是「旧值 +1」而是**按真实行数重算**：
计数一旦因为别的原因漂了，下一次评论就会把它拉回来，
而不是把错误一直累积下去。

**发布帖子请求体（阶段 12d）：**

```json
{
  "title": "分享一个防诈骗经验",
  "content": "……",
  "category_id": 5
}
```

## 11. 认证说明

**V1.0：** 采用简单 JWT 认证。受保护接口需携带请求头：

```text
Authorization: Bearer <token>
```

**需要认证的接口：** 收藏、历史、社区发帖/评论/点赞、个性化设置
**无需认证：** 健康检查、分类、知识列表/详情、AI 问答（V1.0）

> 这条边界是刻意的：安知是安全科普应用，用户可能在起火、
> 有人触电的当口打开它。**浏览知识、搜索、问 AI 一律不要登录** ——
> 一道多余的登录墙会延误他拿到处置方法。这是安全问题，不是体验问题。
> 只有「这份数据属于谁」才有必要问「你是谁」。

### `POST /api/auth/register`

**请求体：**

```json
{ "username": "xiaoming", "password": "hunter2hunter2", "nickname": "小明" }
```

**响应 201：**

```json
{
  "access_token": "eyJhbGciOi...",
  "token_type": "bearer",
  "expires_in": 604800,
  "user": { "id": 1, "username": "xiaoming", "nickname": "小明", "avatar_url": null, "study_days": 0 }
}
```

注册成功即返回 token，**不需要再登录一次**。

**错误：**

| 状态码 | 场景 |
|---|---|
| `400` | 用户名少于 3 或超过 20 个字符；密码少于 8 位或超过 72 字节 |
| `409` | 用户名已被注册 |

> **口令长度按字节算，不是字符。** bcrypt 的上限是 72 **字节**，
> UTF-8 下一个汉字占 3 字节 —— 25 个汉字就会超。
> 服务端显式校验并返回中文说明，而不是让 bcrypt 抛异常变成 500。

### `POST /api/auth/login`

**请求体：**

```json
{ "username": "xiaoming", "password": "hunter2hunter2" }
```

**响应 200：** 与注册相同

**错误：** `401` —— `用户名或密码不正确`

> **用户名不存在与密码错误返回同一句话**，状态码也相同。
> 分开提示等于对外提供了一个「这个用户名注册过没有」的查询接口。

### `GET /api/auth/me`

返回当前 token 对应的用户，用于 App 启动时确认本地凭证是否还有效。

**响应 200：** 与上方的 `user` 字段结构相同
**错误：** `401` —— `请先登录`

> token 签名有效**不等于**用户还在。用户被删除后，旧 token 在过期前
> 依然能通过验签，因此本接口会回数据库确认一次。

### 密钥配置

`JWT_SECRET` 只存在于 `backend/.env`，代码里**没有默认值**。
生成办法与缺省行为见 `backend/.env.example`。缺省时：

| 环境 | 行为 |
|---|---|
| `APP_ENV=development` | 每次启动随机生成临时密钥，启动日志给出警告；**后端一重启，所有已登录用户都要重新登录** |
| `APP_ENV=production` | **直接拒绝启动** —— 宁可起不来，也不用一把重启即失效的密钥对外提供登录服务 |

> **API Key 安全（PROJECT_SPEC 第四十六节）：** DeepSeek API Key 仅存于后端 `.env`，
> Flutter 端不持有、不传递任何第三方密钥，全部经 FastAPI 中转。
